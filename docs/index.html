Reusable GitHub Actions workflow

Test the install, not just the build.

installer-ci looks at your repo, works out which installer types it produces, and runs a real lifecycle for each one on GitHub-hosted runners: build, install, launch, upgrade over the previous release, uninstall.

Add it to a repo View on GitHub

.github/workflows/installer-test.yml in your repo

jobs:
  installer-test:
    uses: scottconverse/installer-ci/
      .github/workflows/installer-test.yml@main
    permissions: { contents: read, packages: read }
    secrets: inherit

A green build can still ship an installer that does not install.

The workflow is built around one rule: it must never false-pass. Each leg captures real exit codes, asserts the artifact exists, launches the real installed program rather than a wrapper process, and asserts that uninstall actually removed things. Repos with no installer, such as prompt or skill suites, no-op green: detection finds nothing and the test job is skipped.

Auto-detects

Reads manifests in the checkout and builds a matrix of installer type and runner OS. No per-repo configuration is required for the default types.

Tests the whole lifecycle

Build, install, launch, upgrade from the latest published release, uninstall, then a check that the lifecycle actually completed.

One place to fix

Callers pin @main, so a fix to the workflow reaches every caller on its next run. Tag the repo and switch callers to a tag if you want immutability.

The lifecycle each detected type runs

Steps are defined per installer type in the recipes. Where a type has user and system install scopes, system scope is on by default (enable_system_scope).

  1. BuildBuilds the artifact in the job and fails on a non-zero exit. It never assumes a prebuilt dist folder.
  2. InstallSilent install with the exit code captured and asserted. The artifact is checked to exist first.
  3. LaunchStarts the real installed program and asserts that process is alive. GUI apps launch headless on Linux.
  4. UpgradeInstalls the previous published release, then upgrades over it. No prior release is treated differently from a failed download.
  5. UninstallUninstalls, then asserts the binary and install directory are gone.

Tripwire. A leg that reaches the end of its lifecycle writes a marker. A matrix leg that skipped its whole lifecycle fails instead of reporting green.

Guards against false passes

The workflow comments label its checks G1 to G8. These are the ones the source states explicitly.

  • Exit codes. Installer and build exit codes are captured and asserted, not swallowed.
  • Artifact exists. The built artifact is resolved and asserted before any install is attempted.
  • Real launch. The installed binary path is matched, so a wrapper or helper process cannot satisfy it.
  • Real upgrade. A genuine prior release is downloaded and installed first. "No prior release" takes a graceful skip with a notice; a failed download does not.
  • Negative uninstall. The install directory, binary or package must be gone afterwards.
  • Signing is warn-only. Signing and notarization are checked, but public CI without signing secrets is not blocked.

Inputs and config

Two workflow inputs, plus optional repository Actions variables.

  • force_types: comma-separated list that overrides detection. It is validated against the 13 known types; an unknown value fails the run instead of creating an empty leg.
  • enable_system_scope: also run system-scope install paths. Default on.
  • Tauri reads vars.TAURI_PRODUCT_NAME, vars.APP_DIR (default .) and vars.TAURI_DIR (default src-tauri).
  • Permissions needed: contents: read, plus packages: read for container image pulls.

Use it in a repo

Add the caller as .github/workflows/installer-test.yml and set the branches to your default branch. This is the form the repo README shows.

Or use the onboarding helper, which opens a pull request and is idempotent. It needs the gh CLI signed in.

./bootstrap.sh <repo>      # one repo
./bootstrap.sh --all         # every repo

ROLLOUT.md also plans a template repo and a weekly sweep so new repos get the caller too.

name: installer-test
on:
  push: { branches: [main] }
  pull_request: { branches: [main] }
  workflow_dispatch:
jobs:
  installer-test:
    uses: scottconverse/installer-ci/.github/workflows/installer-test.yml@main
    permissions: { contents: read, packages: read }
    secrets: inherit

Status, stated plainly

Early. Read this before relying on it.
  • Only the tauri recipe has been through the adversarial review pass. The other 12 are drafted and lint-clean (actionlint) but their guards are not yet independently verified. This is the workflow header's own statement.
  • VERIFY-FINDINGS.json records 24 review findings (4 critical, 8 high, 8 medium, 4 low). This page does not claim which have been resolved; read the file and the commit history.
  • The repository has no license file at the time of writing.
  • The scheduled sweep and template repo described in ROLLOUT.md are plans in that document. There is no sweep workflow in this repo.
